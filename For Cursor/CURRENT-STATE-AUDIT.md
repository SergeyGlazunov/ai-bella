# AI-Contour: аудит текущего состояния

**Дата среза:** 2026-10-12  
**Область:** содержимое папки `D:\contour_gpt`; без изменения кода и живого стенда.

## 1. Итог

Проект представляет собой установочный комплект внутреннего AI-контура для аналитиков 1С. В нём есть:

- Python-оркестратор `contour` для согласованного обновления УБД и двух индексов;
- Docker/Compose-рецепты Graph MCP, query-builder, BSL indexer и чат-слоя;
- отдельные ai2-overlays для УБД, КБ и `klon_opl`;
- PowerShell-скрипты выгрузки КБ и `klon_opl`;
- эксплуатационная документация, stand-gates и unit-тесты оркестратора.

Текущее состояние нельзя считать готовым релизом или подтверждённым состоянием стенда:

1. Папка не является Git-репозиторием, поэтому нельзя установить версию, происхождение файлов и состав локальных изменений.
2. Живой стенд недоступен из этой среды. Docker-контейнеры и задания Планировщика на текущем хосте не совпадают с описанными в документации.
3. Актуальный курс на единый runtime ai2 оформлен только как черновик от 2026-10-12 и реализован частично.
4. Текущий тестовый прогон не воспроизводится: во всех доступных Python отсутствуют `pytest` и `PyYAML`. Синтаксическая компиляция Python проходит.
5. Документация подробно описывает систему, но её сводка и release manifest отстают от последних файлов и решений.

Рекомендуемый курс: сначала стабилизировать существующий PowerShell/ai2-путь для УБД, КБ и `klon_opl`, доказать один полный цикл и следующую ночь, затем отдельно решать вопрос о переходе на `contour`. Не смешивать эти две программы работ.

## 3. Граница достоверности

Этот аудит подтверждает только комплект в `D:\contour_gpt`.

Документация называет живым стендом `ADM-SAPHX-TECH` с контейнерами `mcp-metadata-graph`, `bsl-indexer`, `ai-stack` и заданиями `UBD Config Sync` / `AI-contour ...`. На доступном хосте таких контейнеров и заданий нет. Здесь запущен другой Docker-набор (`mcp-server`, `embedding-service`, `qdrant`, `mcp-inspector`). Поэтому утверждения о prod и ai2 пока являются журнальными свидетельствами, а не результатом текущей проверки.

Не подтверждены:

- фактические версии и health контейнеров prod/ai2;
- актуальность `/srv/ai2/{ubd,kb,klon_opl}/src`;
- совпадение исходников и индексов;
- успешность последних ночных заданий;
- состояние backup/restore чат-слоя;
- действующие URL инструментов в Open WebUI;
- отсутствие конфликтующих старых writer-контейнеров.

## 4. Сильные стороны

1. Хорошо сформулированы инварианты: fail-closed, один writer, FF-only, проверка SHA/storage/image, запрет ложного успеха.
2. Оркестратор разбит на небольшие модули; тесты покрывают lock, окно записи, close/open reads, Docker jobs, Git FF, verify и recovery.
3. Отделены install-kit, prod и параллельный ai2-контур.
4. Есть явные запреты на опасные действия с чат-слоем и томами.
5. Есть stand-gates и процедура cutover/rollback.
6. Секреты отделены от примеров и исключены через `.gitignore`.

## 5. Основные проблемы и риски

### P0 — мешает подтвердить состояние

1. **Нет истории Git.** Невозможно провести diff-аудит, проверить авторство, теги, commit SHA и незакоммиченные изменения.
2. **Нет доступа к описанному стенду.** Главные эксплуатационные утверждения нельзя проверить из этой среды.
3. **Нет воспроизводимой тестовой среды.** `requirements.lock` содержит только runtime-зависимость `PyYAML`; dev-зависимости не закреплены. Текущие 112 тестов не запускаются без ручной подготовки среды.

### P1 — эксплуатационные риски

1. **Два конкурирующих курса:** целевой `contour` и временный PowerShell/ai2. Это повышает риск расхождения логики, имён контейнеров и критериев успеха.
2. **Новый nightly-контур неполон:**
   - нет общего слоя `tools/common/`;
   - нет канонического `tools/ubd/` entrypoint;
   - КБ делает dump, copy и full graph reindex, но code-index не входит в тот же обязательный success path;
   - `klon_opl` делает dump и copy, но не code-index;
   - единая фазовая фиксация результата и sync-lock для трёх баз не реализованы в комплекте.
3. **Нет свежего доказательства end-to-end.** Unit-тесты не доказывают согласованность реальных исходников, Graph MCP и BSL-индекса.
4. **Rollback чат-слоя не доказан drill-процедурой.** Это прямо отмечено в `USER.md`.

### P2 — управляемость комплекта

1. `DEVELOPMENT.md` начинает сводку с 2026-09-21, хотя ниже есть изменения от 2026-10-09, а отдельный design draft датирован 2026-10-12.
2. `release-manifest.json` датирован 2026-09-20 и не отражает новый design draft и текущие PowerShell-изменения.
3. `TECHNICAL-AUDIT.md` — описание решения для аудитора, а не независимый аудит. В нём нет результатов свежего тестового и stand-прогона.
4. В комплекте находятся generated-артефакты: `__pycache__`, `.pyc`, `contour.egg-info`, `.pytest_cache`. `.gitignore` закрывает только часть из них.
5. Bootstrap обновляет `pip` и ставит hash-free зависимости из сети. Для воспроизводимого релиза нужны фиксированный процесс сборки и проверяемый артефакт.

## 6. Рекомендуемый дальнейший курс

### Этап A. Восстановить проверяемость

- определить канонический Git remote/ветку/commit и восстановить `.git` либо получить чистый клон;
- завести повторяемую dev-среду и отдельный lock для тестов;
- запустить unit-тесты с нуля, а не опираться на cache;
- убрать generated-артефакты из поставки;
- обновить manifest, дату среза и контрольную сумму релизного архива.

### Этап B. Завершить текущий PowerShell/ai2 nightly

- реализовать общие Docker/copy/index/logging helpers;
- добавить канонический UBD nightly entrypoint;
- включить обязательный BSL code-index для КБ и `klon_opl`;
- добавить общий lock, фазовый статус и правило «skip обязательного слоя = failure»;
- синхронизировать реальные имена контейнеров и порты с документацией.

### Этап C. Доказать работу на стенде

- снять read-only inventory prod и ai2;
- выполнить один controlled catch-up для трёх баз;
- проверить свежесть исходников, graph fingerprints, BSL index и ответы MCP;
- проверить следующую плановую ночь;
- только после этого убрать старые prod writer-контейнеры, сохранив volumes.

### Этап D. Отдельно решить судьбу `contour`

После стабилизации ai2 выбрать один из вариантов:

1. оставить PowerShell как официальный оркестратор и сократить/архивировать конкурирующий `contour`;
2. провести отдельный проект cutover на `contour` с backup drill, gates и rollback.

До этого `contour` следует считать перспективным кодом, а не действующим runtime.

## 7. Критерий окончания ближайшего этапа

Ближайший этап можно считать завершённым, когда одновременно выполнены условия:

- чистый клон проекта собирается и запускает все тесты одной документированной командой;
- УБД, КБ и `klon_opl` проходят полный nightly без пропущенных обязательных шагов;
- исходники и индексы подтверждены на одном актуальном состоянии;
- следующий автоматический запуск завершается успешно;
- документация и release manifest описывают фактическую схему стенда;
- для каждого изменения есть понятный откат.
