# Design: brainstorming для Беллы

**Date:** 2026-11-20  
**Status:** принят  
**Product:** skill `brainstorming`

Этот файл — контракт первой версии. План и код пишутся после его приёмки. Источник методики — текущий `obra/superpowers`, skill `brainstorming`, обрезанный на согласованной спецификации.

## 1. Problem

Белла — чат аналитиков и заказчиков. Им нужен разбор задачи до design-doc, который другой человек или агент забирает на план и реализацию. План, TDD и исполнение в этом чате не делаются.

Готовый порт `tkalevra/SuperPowersWUI` для этого не берём. Он давно не обновлялся, тащит фазы после spec и собственную проверку shell-команд, которой в `obra/superpowers` нет. Его brainstorm останавливается после одного уточняющего вопроса.

## 2. Goals / non-goals

**Goals**

1. Точка входа — skill `brainstorming`, который пользователь вызывает в чате. Open WebUI подгружает его текст до ответа модели. Своего tool, который возвращает этот текст, нет.
2. Дальше skill ведёт модель чата: вопросы, варианты, design-doc, самопроверка, остановка. Заметки и карточка ЗР читаются уже существующими tools.
3. Число вопросов не ограничено. Один вопрос за сообщение. Следующий вопрос задаётся, пока ответ меняет spec.
4. Архитектурное или инженерное решение не навязывается заказчику. В spec оно записано как «на усмотрение разработчиков»: рекомендация, одна или две альтернативы, ограничения, которые верны для всех вариантов. Выбор делает разработчик на этапе плана.
5. Готовая spec лежит в личной заметке Open WebUI. Повторное сохранение обновляет ту же заметку.
6. Перед вопросами модель ищет заметку. Карточку заявки в SDMS открывает, когда в разговоре есть номер ЗР.

**Non-goals**

- План, список задач, код, тесты реализации, git worktree, субагенты, visual companion.
- Свой tool `brainstorm` и любая обёртка, которая только отдаёт текст skill.
- Второй LLM, режимы cook/ask, Fileshed, запись spec на диск контейнера.
- Общие заметки и выдача доступа группе. `write_note` создаёт личную заметку, так и оставляем.
- Поиск заявок SDMS по названию. Поиск по номеру есть, полнотекстового tool нет.
- Запись в SDMS.

## 3. Decisions

Думает модель, выбранная в чате. Толстый сценарий со вторым LLM отклонён. Отдельный tool со текстом skill тоже отклонён: вызов skill уже кладёт этот текст в чат.

Хранение — встроенные tools Open WebUI: `search_notes`, `view_note`, `write_note`, `replace_note_content`. Свой `save_spec` не делаем.

Заметка личная. Её видит автор, пока сам не откроет доступ в интерфейсе заметок. При создании модели говорит об этом один раз.

## 4. What the user gets

Пользователь вызывает skill `brainstorming` и в том же или следующем сообщении описывает задачу или приносит номер заявки. Модель уже видит текст skill и работает по нему.

Конец сессии: пользователь принял текст spec, заметка создана или обновлена, модель называет id заметки и останавливается. План не предлагает.

## 5. Entry

Пользователь вызывает skill так же, как остальные skills Беллы. Выбранный skill Open WebUI загружает до ответа модели. Модель не вызывает tool, чтобы «получить инструкцию».

Skill не выбран — этой процедуры нет. Модель не ведёт brainstorm по памяти и не предлагает план с кодом вместо spec.

Заметки и SDMS — чужие tools, skill только говорит, когда их звать: `search_notes`, `view_note`, `write_note`, `replace_note_content`, `sdms_get_devrequest`.

## 6. Skill

Файл `integrations/skills/webui/brainstorming.md`, frontmatter как у остальных skills Беллы:

```text
name: brainstorming
description: ведёт задачу до согласованного design-doc и личной заметки. Без плана и кода.
```

Импорт skill в Open WebUI — вручную, как у `integrations/skills/webui/`.

### 6.1. Старт, до вопросов

1. Текст skill уже в чате, потому что пользователь его вызвал. Отдельным tool его не запрашивать.
2. Номер заявки — токен `ЗР` и цифры, дефис между ними допустим (`ЗР000347166`, `ЗР-000347166`). Канон для поиска и заголовка — без дефиса: `ЗР` сразу плюс цифры.
3. Номер есть:
   - `search_notes` с каноном, `count` = 10.
   - `sdms_get_devrequest` с тем же номером. Ошибка или отсутствие tool: сказать, что карточка заявки не прочитана, и продолжать по чату. Текст заявки не выдумывать.
4. Номера нет: `search_notes` по отличительным словам предмета, не по всему сообщению пользователя. SDMS по названию не вызывать.
5. Совпадение по номеру — заголовок или строка `ЗР: {канон}` содержит этот канон. Одна такая заметка: `view_note` и продолжать её. Кратко сказать, что уже решено, и спрашивать только открытое. Несколько таких: показать заголовки и даты и спросить, какую продолжать. Новую не создавать, пока пользователь не выберет.
6. Совпадение только по словам, без номера в заметке: показать заголовки и спросить, продолжать одну из них или начать новую. Молча такую заметку не подхватывать.
7. Ничего не найдено: новая spec.

### 6.2. Вопросы

Один вопрос в сообщении. Лимита на число вопросов нет.

Задавать следующий, пока ответ меняет требования, границы, критерий готовности или выбор поведения.

Остановиться, когда очередной ответ spec уже не изменит, либо открытый пункт — архитектура или способ реализации. Такой пункт не задавать заказчику как обязательный выбор.

### 6.3. Инженерные решения

Если вопрос про архитектуру или про то, как именно это сделать:

- в spec есть рекомендуемый подход;
- рядом одна-две альтернативы;
- отдельной строкой ограничения, верные при любом выборе;
- пометка «на усмотрение разработчиков» — окончательно решает разработчик на плане.

Поведение продукта (что система должна делать для пользователя) по-прежнему выбирает человек в чате. Для него модель предлагает 2–3 подхода. Если человек отказывается выбирать, а пункт на самом деле инженерный, срабатывает пометка выше.

### 6.4. Как собирать текст

Короткие куски design-doc, после каждого — согласие. Затем цельный текст spec на языке разговора.

Факты, которых не было в чате, в карточке SDMS или в ответе tool, не дописывать. Если без факта spec меняется — спросить. Имена объектов конфигурации 1С только из чата, SDMS или другого tool. Иначе спросить или пометить «имя не установлено».

Шаблон spec, порядок разделов фиксирован:

1. Заголовок.
2. Проблема.
3. Цели и не-цели.
4. Уже принятые решения.
5. Подходы: выбранный либо блок «на усмотрение разработчиков».
6. Поведение и контракты: наблюдаемый результат, не раскладка по файлам.
7. Открытые инженерные пункты. Каждый: рекомендация, альтернативы, ограничения, пометка «на усмотрение разработчиков». Пустой список, если таких пунктов нет.
8. Приёмка: как автор плана поймёт, что spec выполнена.

Плана, задач и кода в этом тексте нет.

### 6.5. Самопроверка до просьбы принять spec

Та же проверка, что у ревьюера spec в `obra/superpowers`. Делает модель чата, второго вызова нет.

Смотреть только то, из-за чего план уедет не туда:

- незаполненные места, «TBD», «потом решим» без пометки «на усмотрение разработчиков»;
- противоречия внутри текста;
- формулировка, которую можно исполнить двумя разными способами, и это не помечено как инженерный выбор;
- в одном документе несколько независимых систем;
- функции, о которых не просили.

Нашлась такая дыра — править spec и показать снова. Мелкий стиль не задерживает.

### 6.6. Заметка

Писать заметку, когда пользователь явно принял spec или явно попросил сохранить черновик.

Заголовок: `{канон ЗР} — {короткое название}`. Номера нет — только короткое название.

Первая строка тела: `ЗР: ЗР000347166` либо `ЗР: нет`. Дальше markdown spec.

Обновление, в одном ответе модели, в этом порядке:

1. Id уже известен из этого чата — брать его. Иначе `search_notes`: по канону ЗР, а если номера нет — по словам заголовка.
2. Без id из этого чата заметка, найденная только по словам, не обновляется сама. Спросить, её ли менять. Совпадение по канону ЗР в заголовке или в строке `ЗР:` — обновлять; если таких несколько, спросить.
3. Перед записью в том же ответе вызвать `view_note`. Затем `replace_note_content` с полным новым markdown. `page_id` не передавать у одностраничной заметки. Страниц несколько — тот `page_id`, который вернул `view_note` для текста spec.
4. `replace_note_content` ответил, что страницу не читали — один раз `view_note` и повтор в этом же ответе.
5. Подходящей заметки нет — `write_note`.
6. Повторный `write_note` при уже выбранной заметке запрещён.

Ошибка записи: показать текст ошибки, spec оставить в чате.

После успешной записи назвать id и заголовок. Если заметка только что создана — одна фраза, что она видна только автору, пока он не откроет доступ. Затем остановиться. План, задачи и код не начинать.

## 7. Errors

| Ситуация | Что делает модель |
|---|---|
| Skill `brainstorming` в чат не вызван | Процедуру не начинать и не восстанавливать её по памяти. |
| SDMS недоступен или карточка не открылась | Сказать об этом. Продолжать по чату. |
| `search_notes` вернул ошибку | Сказать об этом. Новую заметку не писать, пока поиск не прошёл: иначе появится дубль. |
| Несколько заметок | Спросить, какую обновлять. |
| `write_note` / `replace_note_content` вернул ошибку | Показать ошибку. Текст spec остаётся в чате. |
| Пользователь просит план или код | Отказать и напомнить, что результат этой работы — spec в заметке. |

## 8. Testing

Автотест `integrations/skills/webui/test_brainstorming_skill.py`. Запуск из корня репозитория:

```text
python -m pytest integrations/skills/webui/test_brainstorming_skill.py
```

Проверки по файлу `brainstorming.md`:

- есть имя `brainstorming`;
- нет лимита на число вопросов, есть «на усмотрение разработчиков»;
- названы `search_notes`, `write_note`, `replace_note_content`, `sdms_get_devrequest`;
- план и код запрещены;
- нет своего tool `brainstorm`, Fileshed и пути `/app/backend/data`.

Поведение модели в живом чате тестом не доказывается. Проверка руками: новый чат, вызван skill `brainstorming`, сообщение с номером `ЗР…`. Модель ищет заметку и заявку и задаёт один вопрос. Tool `brainstorm` не появляется.
