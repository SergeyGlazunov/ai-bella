# Сервис мониторинга и управления контуром

Дата: 2026-10-19
Статус: проект спецификации сохранён для продолжения позже по просьбе пользователя. Выбран стек FastAPI + Jinja2 + HTMX; подробный план и реализация отложены. Документ целиком ещё не утверждён.
Основа: origin/main, коммит 69a23ee; [исторический проект установщика](../superpowers/specs/2026-10-18-installable-contour-design.md). Очерёдность работ: [README.md](README.md).

## 1. Назначение и согласованные решения

На чистой установке оператор видит состояние баз и MCP, последние успешные обновления индексов и причины сбоев. Администратор может повторить обновление одной базы и перезапустить сервис этой базы. Это часть общего слоя устанавливаемого комплекта, в том же репозитории.

Согласовано пользователем:

- Отдельный контейнер с дашбордом и API; API на FastAPI, HTML-шаблоны Jinja2, обновление частей страницы через HTMX.
- Учётные записи и роли Open WebUI. Пользователь смотрит, admin управляет.
- Индексация по ручному запросу запускается сразу, без ожидания ночного окна. При занятом общем lock запрос ждёт.
- Перезапуск только сервисов баз. Чат, OmniRoute, общие MCP и сам мониторинг из API не перезапускаются.
- Индексация и перезапуск используют серверную очередь. Ожидающее задание можно отменить; запущенное в v1 отменить нельзя.
- Сохраняются один писатель, проверка индексов перед публикацией и изоляция независимых баз.

Технические решения ниже предложены для проверки вместе с документом. Реализация и изменение стенда в эту работу не входят.

## 2. Что уже есть

controller/src/contour/db.py содержит database_state, layer_state, runs, jobs и meta. state.py сохраняет ревизии и этапы. cli.py предоставляет contour status и contour update --database. lock.py реализует общий flock. Оркестратор учитывает контейнеры и Docker exec, включая незавершённых писателей после сбоя.

Сейчас status выдаёт текст. HTTP API, серверной очереди административных действий и обхода ночного окна для ручного запроса нет. schedule.py проверяет окно даже для обычного ручного CLI-запуска. Нужен явный режим запуска, который учитывается во всех проверках начала этапов.

layer_state.updated_at меняется и при ошибке. Он не является временем последнего успешного обновления. Историческая applied_revision также не доказывает, что частично перезаписанный индекс сейчас исправен.

## 3. Компоненты и развёртывание

### Контейнер monitor

Один процесс FastAPI обслуживает HTTP API, HTML-шаблоны Jinja2 и адаптер авторизации Open WebUI. HTMX обновляет части страницы и отправляет действия пользователя; его статические файлы входят в образ. Контейнер читает готовые снимки и передаёт разрешённые команды исполнителю. Не монтирует Docker socket, исходники баз, state.db или базу пользователей WebUI. Не выполняет shell-команды.

### Хостовый сервис contour-control

Отдельный systemd-сервис из того же Python-пакета contour. Содержит сборщик состояния, обработчик запросов и последовательный исполнитель очереди. Длинная индексация не блокирует обслуживание запросов статуса и отмены ожидающих заданий.

Связь с monitor: HTTP через Unix socket /run/ai-contour/control/control.sock. В контейнер монтируется каталог socket; права ограничены пользователем сервиса и выделенной группой. TCP-порт управления на хосте не публикуется. Исполнитель принимает операции update_database, restart_service, cancel_action с идентификаторами из конфигурации, а не команды или пути от клиента.

На хосте остаются SQLite и существующий Docker-доступ. Сборщик получает профили из конфига и состояние из contour; интерфейс не разбирает текст CLI. Для status и API используется общий структурированный слой чтения.

### Установка

Комплект устанавливает contour-control, создаёт каталог socket, запускает monitor в общем compose-проекте contour. Порт задаётся конфигом, свободный порт проверяется до запуска. Ноль профилей означает рабочий пустой дашборд. Префиксы ai2, фиксированные имена баз и порты живого стенда в шаблон не переносятся.

Недоступность Docker оставляет хостовый control работающим, но контейнерный дашборд при остановке самого Docker недоступен. Это ограничение v1; внешнего мониторинга хоста здесь нет. Код не меняет живой стенд без отдельного разрешения.

## 4. Вход и права

В проекте закреплён Open WebUI v0.11.4. В его исходниках auths.py текущий пользователь доступен через GET /api/v1/auths/; ответ содержит id и актуальную role. Проверка серверная, через существующую сессию WebUI. Общий JWT signing secret и пароли в мониторинг не копируются.

Для v1 публичные URL WebUI и мониторинга используют одинаковое имя хоста и совместимую схему HTTPS; порты могут отличаться. Cookie WebUI token с Path=/ передаётся браузером и на порт мониторинга. При отсутствии сессии интерфейс показывает ссылку на вход в Open WebUI и предлагает вернуться после входа. Автоматический OAuth/SSO redirect flow и разные домены в v1 не обещаются. Интеграционная проверка реального cookie-поведения обязательна до реализации интерфейса входа.

monitor передаёт полученный credential хостовому control через socket; control проверяет пользователя в WebUI. Credential хранится только в памяти запроса, не в SQLite, логах, URL или argv. Ответ WebUI, содержащий токен, целиком клиенту мониторинга не возвращается.

Роли user и admin могут читать мониторинг; pending и неизвестные роли доступа не получают. Любой admin может создать или отменить ожидающее действие; в истории сохраняются инициатор и отменивший. Каждая команда и отмена требуют свежей серверной проверки admin. Чтение также требует действующей сессии. Недоступность WebUI даёт явную ошибку проверки входа, не анонимный доступ.

Для изменяющих запросов с cookie обязательны проверка Origin и CSRF-токен. Все HTML-маршруты и API защищены, включая запросы HTML-фрагментов через HTMX. Браузерные поля role и user_id не являются доказательством прав.

Права проверяются при принятии команды. Принятая команда продолжает жить после закрытия страницы или истечения сессии; это зафиксированное административное поручение. Повторная авторизация при исполнении не требуется, секрет сессии в очередь не сохраняется.

Источники проверки интерфейса Open WebUI:
- https://github.com/open-webui/open-webui/blob/v0.11.4/backend/open_webui/routers/auths.py
- https://github.com/open-webui/open-webui/blob/v0.11.4/backend/open_webui/utils/auth.py

## 5. Состояние и проверки

API возвращает раздельно состояние обновления, доступность сервисов и свежесть наблюдения. Одно зелёное поле не заменяет эти признаки.

Для базы: enabled, наличие источника, lifecycle, полученная/подготовленная/опубликованная ревизия, текущий этап, последние попытка и успех, причина ошибки, необходимость восстановления. waiting, disabled и отсутствие графа по профилю не считаются аварией. Отсутствие новых исходников не означает устаревший индекс.

Для каждого индекса: status, applied_revision, last_index_succeeded_at, last_verified_at. Для базы: last_published_at. Успех задания индексатора и успешная проверка слоя различаются. Новые отметки сохраняются в SQLite только соответствующим этапом оркестратора. Миграция оставляет исторически неизвестное время NULL; UI показывает «Нет данных». Удаление старых runs не удаляет эти отметки.

Для сервиса: желаемое состояние, фактическое состояние контейнера, ответ MCP, результат проверочного чтения, checked_at, краткая ошибка и время ответа. Остановка на время индексации отображается как обслуживание. Ошибка наблюдения даёт unknown, а не down или последний зелёный результат без оговорки.

Сборщик делает лёгкие проверки каждые 30 секунд, функциональное проверочное чтение раз в 5 минут; HTTP-проверка имеет таймаут 5 секунд. Интервалы настраиваемые. Снимок старше 90 секунд помечается stale, отдельная функциональная проверка старше 10 минут тоже устарела. Веб-страница читает снимок каждые 15 секунд; скрытая вкладка прекращает опрос и обновляется при возвращении. Число открытых страниц не увеличивает число probes. Функциональные проверки выполняются последовательно.

Для graph/code-index/query-builder используются адаптеры их реального транспорта и безопасные чтения. TCP-порт или tools/list без успешного чтения не означают работоспособность данных. При отсутствии подходящей контрольной записи функциональная проверка отмечается not_configured; результат не выдумывается. Во время закрытого чтения функциональные probes базы пропускаются.

Общие MCP отображаются отдельно. Для SDMS/Confluence состояние установленного tool и доступность сервиса не доказывают доступ с личными ключами каждого пользователя; это явно указано в UI. Личные ключи мониторинг не собирает. Сервисные MCP-секреты сборщик читает из существующих настроек хоста.

Время хранится в UTC, показывается в Asia/Vladivostok с указанием зоны. В v1 нет графиков нагрузки, отдельного хранилища метрик и новых каналов оповещения.

## 6. Очередь и отмена

Новая таблица admin_actions в существующей SQLite: id, kind, database, service_id, state, requested_by, requested_at, started_at, finished_at, cancelled_by, cancelled_at, wait_reason, result_code, message, run_id, idempotency_key, dispatch_phase. Существующие jobs остаются учётом индексаторов; административное действие ссылается на run, а не подменяет jobs.

Состояния: queued, running, succeeded, failed, cancelled, needs_review. Последнее означает, что после сбоя нельзя уверенно определить исход действия. UI показывает понятные русские подписи.

Очередь FIFO, один исполнитель. Пока lock занят, действие остаётся queued и отменяемым. Перед запуском исполнитель получает общий lock, проверяет живых/неизвестных писателей по существующему механизму contour и повторно проверяет профиль и сервис. Одного свободного flock после падения процесса недостаточно для разрешения новой записи.

Переход queued в running выполняется условным UPDATE в короткой транзакции. Отмена делает условный UPDATE queued в cancelled. Только одна операция может изменить исходное состояние; успешная отмена гарантирует отсутствие запуска. Идемпотентная повторная отмена cancelled возвращает тот же результат; отмена running или завершённого задания возвращает 409 и текущий статус.

Повтор HTTP-запроса с тем же Idempotency-Key возвращает исходное действие. Дополнительно одинаковая операция для той же цели, уже queued/running, не создаёт дубль. Отменённая операция допускает новый осознанный запрос с новым ключом.

Очередь переживает закрытие браузера, перезапуск monitor и control. После старта control сначала сверяет running-действия с runs/jobs и Docker. Индексация восстанавливается штатным механизмом contour без второго писателя. Для перезапуска не обещается exactly-once через падение процесса: если команда могла уйти в Docker, но результат не сохранён, действие становится needs_review и автоматически повторно не отправляется. Администратор видит фактическое состояние и может создать новый запрос.

## 7. Выполнение команд

### Обновление базы

Обновляет одну включённую базу штатным pipeline contour. Источник готовится существующим способом; при отсутствии новых данных возможен штатный пропуск. Кнопка не означает принудительный FULL. Отдельная принудительная пересборка не входит в v1.

Для административного action добавляется явный режим manual вне окна, передаваемый до всех проверок запуска этапов. Не изменять глобальный конфиг расписания и не подменять время. Nightly и обычный update сохраняют своё расписание. Lock, проверки источников, проверка индексов и правила публикации действуют и в manual-режиме.

Исполнитель и CLI используют общий сервис запуска pipeline с определённым владельцем lock. Запрещён повторный захват того же lock дочерним contour update. Длинная работа выполняется отдельно от обработчика HTTP, но в управляемом процессе с учётом action/run.

### Перезапуск сервиса

Цели: code-index; при наличии графа также graph MCP, query-builder и Neo4j выбранного профиля. Только существующий контейнер из конфигурации. Не compose up/recreate/pull, не удаление контейнеров или томов. Одноразовые контейнеры индексации не являются целями.

Пока идёт запись, запрос ждёт. Перед выполнением повторно проверить профиль, учёт писателей и допустимость чтения. Если база отключена, ждёт первую выгрузку либо индекс непроверен после сбоя, действие завершается с понятной причиной отказа; restart не открывает закрытые MCP. Для такого состояния требуется обновление/восстановление.

Перезапуск Neo4j предупреждает о недоступности зависимых инструментов этой базы. Успех фиксируется после наблюдения нового запуска и профильных проверок готовности (предлагаемый предел ожидания 120 секунд, настраиваемый). При timeout показать failed и фактическое состояние: это не доказывает, что контейнер остался остановлен. Очередь соседних баз продолжается, если неизвестного писателя нет.

## 8. HTTP API и интерфейс

Все пути ниже относительны к /api/v1 мониторинга, а не WebUI.

| Метод и путь | Назначение |
| --- | --- |
| GET /me | Проверенный пользователь и разрешения |
| GET /overview | Сводка баз, общих MCP и свежесть снимка |
| GET /databases/{id} | Слои, ревизии, сервисы и последний результат |
| GET /databases/{id}/runs | История с ограничением размера страницы |
| GET /actions | Очередь и история административных действий |
| GET /actions/{id} | Состояние действия и ссылка на run |
| POST /databases/{id}/update | Административное обновление |
| POST /databases/{id}/services/{service_id}/restart | Перезапуск сервиса базы |
| POST /actions/{id}/cancel | Отмена ожидающего действия |

Создание возвращает 202 и id/state; принятие в очередь не считается успехом операции. Ошибки: 401 нет сессии, 403 нет роли, 404 неизвестная цель, 409 недопустимое состояние, 503 зависимость недоступна. Тело содержит стабильный code, понятный message и при необходимости action_id. Тексты не содержат секретов.

Главная страница: таблица баз, общий слой и текущие задания. Карточка базы: код и граф, успешные даты, ревизии, доступность MCP, последняя ошибка и история. При нуле баз показывается пустое состояние. Полные логи и произвольный просмотр файлов в v1 не предоставляются.

Для admin есть «Обновить» и «Перезапустить». Перед отправкой показаны цель и влияние на доступность. Для queued отображается причина ожидания и «Отмена». Для running отмена недоступна. После ответа API строка обновляется; гонка с запуском показывает «Задание уже запущено». Отменённые задания остаются в истории.

## 9. Проверки приёмки

1. Установка без баз: monitor отвечает, вход WebUI работает, список пуст; дашборд не требует выгрузок.
2. user читает, но прямой POST управления получает 403; pending не допущен. Снятие admin учитывается следующим запросом. При недоступном WebUI команды не принимаются.
3. Проверить cookie входа/выхода на закреплённой версии WebUI в браузере, CSRF и защиту HTML-фрагментов HTMX и API. Пароли и JWT отсутствуют в логах/SQLite.
4. Даты успеха не меняются при новой неудачной попытке; частично записанный индекс не становится ready из-за старой ревизии.
5. Недоступность MCP при работающем контейнере отображается; остановка для записи отличается от аварии. Пропавший сборщик даёт stale.
6. Ручное обновление днём проходит проверки расписания в manual-режиме, nightly вне окна не начинает запись. Неизвестный живой writer блокирует запуск.
7. Два нажатия не создают два задания; ручной запрос и timer не запускают двух писателей.
8. Отмена queued гарантирует отсутствие Docker-команды. В гонке claim/cancel ровно один переход успешен. После рестарта приложения queued/cancelled не теряются.
9. Падение control при индексации не запускает дубль; неоднозначный restart становится needs_review без автоматического повторения.
10. Restart ограничен сервисами базы; чат и общие MCP недоступны как цели даже при прямом API-запросе. Закрытый после сбоя MCP не открывается перезапуском.
11. После ошибки одной базы независимые базы остаются доступны. Отказ контроля готовности не маскируется успехом Docker-команды.
12. Локальные unit/integration проверки и отдельный compose-стенд проходят до предложения внедрения. Живой стенд требует отдельного разрешения.

## 10. Граница последующего плана

Работа отложена по просьбе пользователя. При возвращении сначала проверить актуальность проекта и оставшиеся решения спецификации, затем согласовать документ. После этого составляется отдельный план реализации: состояние и миграции; очередь/отмена/восстановление; manual-режим и restart; сборщик; WebUI auth и API; интерфейс Jinja2 и HTMX; упаковка и интеграционная приёмка. Это порядок зависимостей, не разрешение начинать реализацию.

Не входят: принудительное завершение running, принудительный FULL, общий Docker-терминал, управление чат-слоем, новая система пользователей, Prometheus/Grafana, новые поколения индексов, перенос стенда и завершение всех остальных пунктов установочного контракта.

## 11. Ресурсы и ограничения виртуальной машины

Расширение виртуальной машины пока недоступно. Выбор FastAPI + Jinja2 + HTMX сделан для небольшого интерфейса статусов и управления. Один веб-процесс; Redis, Celery, отдельный сервер БД и сервер Node.js не добавляются. Используется существующая SQLite; история выдаётся страницами, логи ротируются. Срок хранения административной истории настраиваемый, начальное значение 90 дней; queued, running и needs_review не удаляются по возрасту.

Предварительная инженерная оценка для нескольких баз и 1–5 открытых страниц, не результат измерения:

| Часть | Ориентир памяти |
| --- | --- |
| Веб-контейнер | 50–120 МБ |
| Хостовый исполнитель и сборщик | 40–100 МБ |
| Постоянная дополнительная нагрузка с небольшим запасом | 100–250 МБ |

Для планирования предусмотреть общий бюджет 256–384 МБ. Это ориентир для проверки, не гарантия и не готовый жёсткий лимит. В оценку не входят память браузеров пользователей, существующие сервисы, индексаторы и временные процессы проверок. Пики всей цепочки измеряются отдельно. Цель по CPU: средняя дополнительная нагрузка мониторинга менее 5% одного ядра при пяти открытых страницах, без самой индексации. Достижение цели пока не проверено.

Перед внедрением измерить память и CPU веб-контейнера, хостового исполнителя и дочерних процессов в простое, при пяти открытых страницах, при недоступных MCP и во время запуска задания. Учитывать дополнительную нагрузку probes на проверяемые сервисы. По результатам определить ограничения контейнера и systemd-сервиса; при остановке сервиса из-за лимита очередь не должна теряться или создавать второго писателя.

Объём RAM, число vCPU и свободная память виртуальной машины под индексацией пока неизвестны. При возвращении к задаче получить эти данные до решения о внедрении. Ручная индексация днём может совпасть с нагрузкой чата и MCP; общий lock запрещает второго писателя, но не ограничивает общую нагрузку виртуальной машины. Новый стек сам по себе эту проблему не решает.
