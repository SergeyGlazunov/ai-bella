# Работа со стендом и Git

Действует с 2026-10-29 по решению владельца контура.

## Приоритет

Поддерживаем и дорабатываем работающий контур. Фактическое состояние определяем на стенде; в Git сохраняем его код, конфигурации без секретов и историю изменений. Исправление рабочего контура не обязано решать задачу установки на чистую машину.

Этот порядок имеет приоритет над прежним контрактом устанавливаемого продукта и планами миграции. Технические инструкции применяем только после проверки, что они относятся к текущей версии стенда. Мониторинг и универсальный установщик отложены: [будущие доработки](future-work/README.md).

## Как сохранять изменения

1. Перед работой проверить ветку, SHA, незакоммиченные изменения и какие файлы сейчас меняет другой разработчик или агент. Пока Cursor работает на стенде, не перезаписывать его файлы, не переключать его ветку и не запускать параллельное внедрение.
2. Исправления можно делать непосредственно на стенде в рамках порученной задачи. Если сервис запускается из другой папки или образа, установить, откуда он берёт код, и сравнить его с репозиторием. Переносить проверенные изменения, сохраняя чужую незавершённую работу.
3. Проверить затронутые сервисы. Зафиксировать результат, известные ошибки и ограничения. Наличие ошибки не запрещает сохранить фактическое состояние в Git; её нельзя скрывать за отметкой «успешно».
4. Коммитить связанные изменения отдельно, с описанием причины и проверки. Согласованные изменения со стенда переносить в `main` обычным коммитом или слиянием и пушить в GitHub. Не использовать force push, reset или массовое копирование поверх текущих доработок.
5. Обновить [STATUS.md](../STATUS.md) и [DEVELOPMENT.md](../DEVELOPMENT.md): что действительно работает, что изменено только в коде, что не проверено и что осталось исправить. Если Git ушёл вперёд стенда или стенд содержит незакоммиченные изменения, отметить расхождение явно.

Рабочая ветка допустима для незавершённых изменений. Сам по себе push такой ветки не означает, что `main` отражает продакшен. Цель `main` — проверенная история рабочего контура; будущие эксперименты не выдавать за внедрённые изменения.

## Что хранить

В Git: исходники используемых сервисов и инструментов, Dockerfile, compose, скрипты, настройки расписаний, конфигурации без секретов, зависимости и сведения о версиях образов. Настройки, специфичные для этого стенда, допустимы; помечать их назначение. Для внешнего кода указывать происхождение и версию.

Не добавлять ключи, пароли, токены, пользовательские чаты, содержимое рабочих баз, индексы, Docker volumes, сырые логи и выгрузки 1С. Для них нужны отдельные резервные копии. Если нужные параметры находятся рядом с секретами, сохранять очищенную конфигурацию и способ подстановки значений. Перед коммитом проверить состав и diff, не добавлять всё дерево вслепую.

## Как подтверждать состояние

Каждая сводка содержит дату и часовой пояс, Git SHA рабочей копии, наличие локальных изменений, источник запуска сервисов, версии или ID запущенных образов и результаты относящихся к задаче проверок. Если образ нельзя связать с коммитом, так и записать.

Для ночного обновления указывать результат по каждой базе и слою (исходники, граф, код), время последнего успешного обновления и причину сбоя. Статус контейнера `running` не доказывает готовность MCP или полноту индекса. Коммит не доказывает, что контейнер пересобран и запущен с ним.

Старые аудиты и записи журнала описывают состояние на свою дату. Не переписывать их задним числом и не переносить старые выводы в текущую сводку без проверки.

## Границы текущего решения

Изменение документации не запускает синхронизацию файлов, переиндексацию, перезапуск контейнеров или переустановку стенда. Такие действия выполняются в рамках соответствующей задачи. Существующие правила сохранности данных и проверки индексов остаются в силе.
